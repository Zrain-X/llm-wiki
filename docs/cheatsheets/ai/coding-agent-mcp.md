# Coding Agent / MCP 速查

这页用于快速判断：一个 Agent 为什么能操作项目、工具怎么接、怎样避免“能聊天但不能真正完成任务”。

## Coding Agent 的核心闭环

真正有用的 Coding Agent 通常不是一次生成代码，而是：

```text
读取项目
  ↓
理解约束
  ↓
制定计划
  ↓
修改文件
  ↓
运行构建 / 测试
  ↓
读取结果
  ↓
继续修复
```

缺少“执行工具”和“读取结果”这两个环节，就很容易退化成只会给建议的聊天模型。

## 项目操作最小能力

一个可用的代码 Agent 至少需要：

- 文件读取；
- 精确文件编辑；
- 文件搜索；
- Git diff / status；
- Shell 执行；
- 构建和测试；
- 可选：浏览器 / Playwright 视觉验证。

对于前端项目，**视觉问题必须实际打开页面检查**，不能只凭源码判断“已经修好了”。

## MCP 的定位

MCP 可以把外部能力以统一的工具/资源接口暴露给模型应用。理解时可以把它拆成：

```text
LLM / Agent
    ↓
MCP Client
    ↓
MCP Server
    ↓
Files / Git / DB / Browser / API / Other tools
```

MCP 解决的是“怎样标准化地暴露能力”，不是自动替你解决权限、安全和业务语义。

## 接一个工具前先问四个问题

1. **发现**：Agent 能不能知道这个工具存在？
2. **权限**：它是否真的有读取/写入权限？
3. **上下文**：项目目录、仓库、账号等信息能不能自然传进去？
4. **反馈**：调用失败后，Agent 能不能看到明确错误并继续修复？

很多集成“看起来接上了但不好用”，根因都在这四项之一。

## 本地项目操作的目录问题

如果工具只能操作白名单目录，那么“当前可操作目录”应该尽量成为 Agent 上下文的一部分，而不是每轮都让用户重新解释。

一个理想流程：

```text
连接本地工具
  ↓
工具返回允许的 workspace / project
  ↓
Agent 选择或复用 workspaceId
  ↓
后续读写都基于这个 workspace
```

## 安全边界

公共 Agent / MCP 配置里不要硬编码：

- Token；
- SSH 私钥；
- 数据库密码；
- Cookie；
- 内网地址和敏感拓扑。

凭据应该通过环境变量、Secret Store 或连接器授权传递。

## Coding Agent 做项目时的推荐规则

### 改之前

- 读 README / AGENTS / CLAUDE 等项目说明；
- 看 `package.json` / `pyproject.toml`；
- 找入口、路由和测试命令；
- 先复现问题。

### 改之后

- Build；
- Lint；
- Test；
- 前端问题做浏览器验证；
- 看 Git diff，避免夹带无关修改。

## 多 Agent 什么时候值得用

适合并行的任务：

- 多个互不依赖 Issue；
- 独立模块调研；
- 测试 / 文档 / 实现可以拆开；
- 多种方案横向评估。

不适合盲目并行：

- 多个 Agent 同时改同一文件；
- 高度依赖前一步结论；
- 没有统一合并和验证流程。

关键不是“Agent 越多越快”，而是**任务边界能否清晰拆分**。
