# 磁盘、文件系统与空间排查

Linux 上“磁盘满了”其实可能指完全不同的问题：块设备容量不足、某个文件系统满了、inode 用尽、目录暴涨、已删除文件仍被进程占用，甚至只是你统计了错误的挂载点。

所以磁盘排障的第一原则是：**先确定满的是哪一层，再去找谁占空间。**

## 先建立磁盘到目录的层次关系

可以把常见存储路径理解成：

```text
磁盘/块设备
  ↓
分区 / LVM / RAID
  ↓
文件系统 ext4 / XFS / btrfs ...
  ↓
挂载点
  ↓
目录和文件
```

`lsblk` 看上半层：

```bash
lsblk -f
```

它适合确认：

- 磁盘和分区结构；
- 文件系统类型；
- UUID；
- 挂载点。

`findmnt` 更适合从挂载关系观察：

```bash
findmnt
findmnt /
```

## `df` 回答“文件系统还剩多少”

```bash
df -hT
```

这里：

- `-h`：人类可读单位；
- `-T`：显示文件系统类型。

例如根目录 `/` 使用率 98%，说明要排查的是承载 `/` 的那个文件系统，而不是笼统地说“服务器磁盘满了”。

查看 inode：

```bash
df -i
```

这一步很容易被忽略。

## 容量没满，inode 也可能先用完

文件系统需要 inode 记录文件元数据。大量极小文件可能导致：

```text
磁盘容量还有空间
但已经无法创建新文件
```

这时：

```bash
df -h
```

可能看起来正常，而：

```bash
df -i
```

显示 IUse% 接近 100%。

典型来源包括缓存目录、小文件日志、邮件队列、海量临时文件等。

## `du` 回答“目录树里的文件占多少”

查看某目录一级子目录：

```bash
du -xhd1 /var | sort -h
```

这里 `-x` 很重要：只统计当前文件系统，避免进入其他挂载点。

继续向大目录下钻：

```bash
du -xhd1 /var/lib | sort -h
```

这种“逐层下钻”往往比一开始就在整盘 find 大文件更快，因为很多磁盘问题来自**大量中小文件聚集在一个目录**，不一定存在单个巨型文件。

## `df` 和 `du` 为什么可能对不上

这是 Linux 磁盘排障里的高频经典问题。

### 原因一：文件已经删除，但进程还打开着

Unix 文件被删除后，只是目录项解除链接；只要某个进程仍持有打开的文件描述符，数据块就不会真正释放。

表现为：

```text
df：空间仍然很满
du：找不到对应文件
```

检查：

```bash
sudo lsof +L1
```

如果发现某个巨大日志显示 `(deleted)`，应让对应进程重新打开日志、reload/restart，或者通过应用自身日志轮转机制处理。

不要通过 `/proc/<pid>/fd` 随意截断文件，除非非常清楚应用行为。

### 原因二：统计跨越了挂载点

如果目录下面又挂了其他文件系统，`du` 和目标 `df` 可能根本不在统计同一批数据。

使用：

```bash
du -x ...
findmnt
```

可以减少这种误判。

### 原因三：文件系统保留空间和元数据

文件系统自身也会消耗元数据空间，一些文件系统还保留部分块。因此 `du` 汇总的普通文件大小不必与 `df` 使用量完全相等。

关键是判断差异是否异常大。

## 查找大文件时给 find 加边界

```bash
find /var -xdev -type f -size +1G -printf '%s %p\n' 2>/dev/null \
  | sort -n
```

`-xdev` 避免跨文件系统；`-type f` 只看普通文件。

如果只是想快速看最大的若干个文件，可以再接：

```bash
... | tail
```

但要记住：最大的文件不一定是罪魁祸首。

## Docker 经常让 `/var/lib` 快速膨胀

容器主机上，如果 `/var/lib/docker` 很大，应先用 Docker 自己的视角：

```bash
docker system df
```

再判断是：

- image；
- container writable layer；
- local volume；
- build cache；
- container log。

不要第一反应就是：

```bash
docker system prune -a
```

清理动作可能删除后续仍需使用的镜像、缓存或未使用资源。先看清组成，再定向处理。

## 日志增长问题应该修“增长机制”，不是定期手删

如果某个日志不断把根分区写满，只手工 `rm` 相当于治标。

应继续查：

- 应用是否支持日志轮转；
- logrotate 是否配置；
- journald 是否设置合理上限；
- Docker 日志驱动是否限制大小；
- 是否出现异常错误循环导致日志暴涨。

对于 journal：

```bash
journalctl --disk-usage
```

查看当前占用。

空间治理应该最终落到**保留策略**，而不是靠人工发现后再清理。

## 删除文件后空间不释放，先找持有进程

例如：

```bash
rm app.log
```

但应用仍然向已经打开的 fd 写入，磁盘空间不会立刻回来。

此时：

```bash
sudo lsof +L1
```

确认是谁持有，再根据服务类型做 reload/restart。

这也是为什么日志轮转工具通常会配合应用 reopen 日志，或者使用 copytruncate 等策略。

## 根分区爆满时的一套实用流程

1. `df -hT`：确认真正满的文件系统；
2. `df -i`：排除 inode 耗尽；
3. `findmnt` / `lsblk -f`：确认挂载边界；
4. `du -xhd1 / | sort -h`：一级一级向下找大目录；
5. 对可疑目录再查大文件或文件数量；
6. 如果 `df` 与 `du` 差异很大，运行 `lsof +L1`；
7. 容器主机用 `docker system df`；
8. 找到根因后再决定归档、压缩、删除或调整保留策略。

## 不要在磁盘 100% 后才开始治理

更理想的运维方式是提前建立：

- 文件系统容量告警；
- inode 告警；
- 日志轮转；
- 备份保留策略；
- 容器镜像/缓存治理；
- 大目录增长趋势监控。

磁盘问题表面上是在“找大文件”，真正要维护的是**数据生命周期和容量边界**。
